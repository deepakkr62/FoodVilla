# 🚀 Deploy Food Villa to the internet

This guide walks you from a fresh repo to a publicly accessible deployment in about 30 minutes.

Architecture:

```
                              ┌────────────────────┐
   Browser  ────HTTPS─────►   │  Vercel (Next.js)  │
                              │  foodvilla.vercel  │
                              └─────────┬──────────┘
                                        │ API calls + WebSocket
                                        ▼
                              ┌────────────────────┐
                              │  Render (Express)  │
                              │  foodvilla-api...  │
                              └─────────┬──────────┘
                                        │ Mongoose
                                        ▼
                              ┌────────────────────┐
                              │  MongoDB Atlas     │
                              │  M0 free cluster   │
                              └────────────────────┘
```

---

## Step 1 — Push to GitHub (5 min)

```powershell
cd "C:\Food Villa"
git init
git add .
git commit -m "Initial Food Villa commit"
# Create a new repo at https://github.com/new (do NOT initialize with README)
git remote add origin https://github.com/<your-username>/food-villa.git
git branch -M main
git push -u origin main
```

After this, GitHub Actions will start running the CI workflow on every push (lint, type-check, unit tests, Playwright E2E).

---

## Step 2 — MongoDB Atlas (already done ✓)

If you've followed the earlier setup, your Atlas cluster is ready. Otherwise:

1. https://www.mongodb.com/cloud/atlas/register → free M0 cluster
2. Database user: `foodvilla_app` with a strong password
3. Network access: temporarily add `0.0.0.0/0` (we'll lock it down to Render's IPs in Step 6)
4. Copy your connection string: `mongodb+srv://foodvilla_app:<pwd>@cluster0.../foodvilla?...`

---

## Step 3 — Deploy the backend to Render (10 min)

1. Open https://render.com/ → Sign up with GitHub
2. Dashboard → **New** → **Blueprint**
3. Connect your `food-villa` repo
4. Render reads `render.yaml` at the root and provisions a web service
5. When prompted, set the **sync: false** values:
   - `MONGODB_URI` → your Atlas connection string
   - `FRONTEND_URL` → `https://foodvilla.vercel.app` (you'll get this in Step 4 — paste a temporary URL like `https://food-villa.vercel.app` for now and update after Step 4)
   - `STRIPE_SECRET_KEY` → `sk_test_replace_me` for now (the dev fallback handles missing keys)
   - `STRIPE_WEBHOOK_SECRET` → `whsec_replace_me`
6. `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are auto-generated by Render — leave them alone
7. Click **Apply**. First build takes ~5 minutes.
8. When done, copy your Render URL: `https://foodvilla-api-XXXX.onrender.com`
9. Verify the health endpoint: `https://foodvilla-api-XXXX.onrender.com/api/health` → should return `{"status":"ok", "db":"connected", ...}`

---

## Step 4 — Deploy the frontend to Vercel (5 min)

1. Open https://vercel.com/ → Sign up with GitHub
2. **Add New… → Project** → import your `food-villa` repo
3. Vercel auto-detects Next.js. **Root Directory**: `frontend` (important!)
4. Add environment variables:
   - `NEXT_PUBLIC_API_URL` = your Render URL from Step 3 (e.g., `https://foodvilla-api-xxxx.onrender.com`)
   - `NEXT_PUBLIC_SOCKET_URL` = same URL
   - `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` = `pk_test_replace_me` (or real key if you have it)
   - `NEXT_PUBLIC_SITE_URL` = your Vercel URL (e.g., `https://food-villa.vercel.app`)
5. Click **Deploy**. First deploy takes ~3 minutes.
6. Once done, copy your Vercel URL: `https://food-villa-xxx.vercel.app`

---

## Step 5 — Wire them together (2 min)

Go back to Render → your service → **Environment** tab:
- Update `FRONTEND_URL` to your actual Vercel URL from Step 4
- Click **Save Changes** → Render auto-redeploys

Done! Open your Vercel URL → sign up → place an order → it all works on the live internet.

---

## Step 6 — Lock down Atlas (security hardening, 5 min)

Right now `0.0.0.0/0` allows anyone with credentials to connect to your DB. Restrict to Render:

1. Render dashboard → your service → **Settings** → scroll to **Outbound IPs** → copy them (usually 3-4 IPs)
2. Atlas → **Network Access** → **+ ADD IP ADDRESS** → paste each Render IP (with comments like "Render outbound 1")
3. Delete the `0.0.0.0/0` entry once Render IPs are confirmed working
4. Reload the app — should still work

---

## Step 7 — Add real Stripe keys (optional, 5 min)

If you want real card payments instead of the dev fallback:

1. https://dashboard.stripe.com/register → sign up
2. Stay in **Test mode** (top-right toggle)
3. Developers → API keys → copy:
   - `sk_test_...` → set in Render as `STRIPE_SECRET_KEY`
   - `pk_test_...` → set in Vercel as `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`
4. Developers → Webhooks → **Add endpoint**:
   - URL: `https://foodvilla-api-XXXX.onrender.com/api/stripe/webhook`
   - Events: `checkout.session.completed`, `checkout.session.expired`
   - Copy the `whsec_...` → set in Render as `STRIPE_WEBHOOK_SECRET`
5. Both services redeploy → real Stripe flow is now live

---

## Step 8 — (Optional) Custom domain

### Vercel
1. Vercel dashboard → your project → **Domains** → Add → enter `foodvilla.in` or whatever you own
2. Follow DNS instructions (usually one CNAME)
3. Update `NEXT_PUBLIC_SITE_URL` in Vercel
4. Update `FRONTEND_URL` in Render

### Render (for API)
Same idea — Render → Settings → Custom Domains → e.g. `api.foodvilla.in`

## Troubleshooting

| Problem | Fix |
|---|---|
| Render shows `db: disconnected` on `/api/health` | Atlas IP allowlist is rejecting Render. Add `0.0.0.0/0` temporarily, verify, then narrow to Render's outbound IPs. |
| Frontend gets CORS errors | `FRONTEND_URL` in Render doesn't match your Vercel URL exactly. Make sure scheme, host and absence of trailing slash match. |
| Socket.io fails to connect | Render's free tier sleeps after inactivity. First request wakes it (10-20s). Bump to paid plan for always-on. |
| Sign-up fails with 500 | Most likely Render hasn't fully booted. Check Render logs, wait 30s, retry. |
| Stripe webhook returns 400 | `STRIPE_WEBHOOK_SECRET` mismatch. Re-copy from Stripe dashboard, paste exactly into Render. |

## CI/CD

The `.github/workflows/ci.yml` workflow runs on every push and PR:

1. **Lint, type-check, unit tests** — both backend and frontend
2. **Playwright E2E** — full browser-driven test of the customer journey

Failed CI runs block merging. Once merged to `main`, both Vercel and Render auto-deploy.

## Resource limits (free tiers)

| Service | Free tier limit | Impact |
|---|---|---|
| Vercel | 100GB bandwidth / month, unlimited static deploys | Plenty for portfolio use |
| Render | 750 hours / month, sleeps after 15 min idle | First request after sleep is slow (10-30s) |
| MongoDB Atlas M0 | 512MB storage, ~100 connections | Way more than you need for v1 |

If you outgrow these, the upgrade paths are clean (Render starter $7/mo never sleeps; Atlas M2 $9/mo dedicated CPU).
